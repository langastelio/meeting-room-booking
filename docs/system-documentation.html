Meeting Room Booking System

System Requirements & Functional Specification

Document version 1.0  |  Date: 10 June 2026  |  Live URL: https://langastelio.github.io/meeting-room-booking/

1. Introduction

The Meeting Room Booking System is a lightweight, web-based application that lets an organisation manage meeting rooms and reserve them for meetings. It enforces access control through user accounts and roles, prevents double-booking of rooms, supports cancellations with reasons, sends meeting reminders, and keeps a full history of meetings for reporting.

The application is a 100% static front-end (HTML, CSS and vanilla JavaScript) hosted on GitHub Pages, backed by a Supabase (PostgreSQL) cloud database accessed directly from the browser. There is no custom application server to maintain.

3. Technology Stack

  • HTML / CSS / JavaScript — user interface and application logic.
  • Supabase (PostgreSQL) — cloud database, accessed with the public publishable key and Row Level Security.
  • SheetJS (xlsx) — reads the seed Excel workbook on first run.
  • GitHub Pages — free static hosting and automatic deployment on push.
  • Web Notifications API — browser notifications for meeting reminders (with in-page toast fallback).

5. Functional Requirements

5.1 Authentication & Access Control

  • Every page requires a signed-in session; unauthenticated visitors are redirected to the login page.
  • First-run setup: when no accounts exist, the login page switches to "Create the first admin" and the first registered account becomes the administrator.
  • Roles: Administrator and Standard User, controlling page access and actions.
  • Forced password reset: accounts created by an admin receive a temporary password and must set their own password on first login before using the app.
  • Idle auto-logout: users are automatically signed out after 15 minutes of inactivity (mouse, keyboard, scroll, touch). Activity in any open tab keeps the session alive; an idle period that spans a closed tab is detected on next load. The login page then displays a notice.
  • Passwords are hashed with SHA-256 (with a salt) before storage; plain passwords are never stored.

5.2 User Management (Admin)

  • Create users with full name, username, temporary password and role (Admin or User).
  • Edit a user's name and role inline.
  • Reset a user's password (issues a new temporary password requiring reset on next login).
  • Enable or disable an account (disabled accounts cannot sign in).
  • Delete a user.
  • Administrators cannot change or delete their own account, preventing accidental lock-out.
  • Usernames are validated against a safe character whitelist (letters, numbers, and . _ - @, 3–50 characters).

5.3 Meeting Room Management (Admin)

  • Add a room with name, location, capacity and facilities.
  • Edit room details inline.
  • Activate / deactivate a room. Inactive rooms retain their data but cannot be booked and do not appear on the booking page.
  • Delete a room (existing bookings are retained).

5.4 Booking a Room

  • Select a room, enter a meeting title, choose a date, and a start and end time.
  • The "Booking as" field is read-only and shows the signed-in person's name; the booking is recorded under that name and account.
  • Conflict prevention (per room): a room cannot be double-booked for overlapping times on the same day. The check is performed against the latest data before saving, so it holds across all users.
  • Alternative suggestions: when a clash occurs, the system suggests (a) other rooms free at the same time, and (b) other free time slots for the chosen room (08:00–18:00, 30-minute steps). Each suggestion can be clicked to re-book instantly.
  • Bookings are shared and synchronised live across all browsers.

5.5 Cancelling a Meeting

  • Cancellation opens an in-app modal requiring a reason.
  • A cancelled meeting is not deleted; it is marked as cancelled and retains who cancelled it, the reason, and the time of cancellation for the audit trail.
  • Cancelled meetings free up the room (the slot can be re-booked) and are removed from the Upcoming list.
  • Standard users can only cancel their own meetings; administrators can cancel any meeting.

5.6 Notifications

  • Meeting reminders: for a user's own upcoming meetings, reminders appear at 30, 15 and 5 minutes before the start time, as a browser notification (if permitted) and an in-page toast. Reminders work while the app tab is open.
  • Admin-cancellation notice: when an administrator cancels a meeting that belongs to another user, that user receives a notification (including the reason) the next time they are on the app.

5.7 Upcoming Meetings & History (Reporting)

  • The booking page lists only upcoming meetings; meetings that have already ended are removed from this list automatically (they are not deleted).
  • The History page (admin-only) lists completed and cancelled meetings, newest first, with a date-range filter.
  • History shows status (Held / Cancelled), who cancelled, and the cancellation reason.
  • History can be exported to a CSV file for reporting.

5.8 User Interface

  • Dark / light theme toggle, remembered per browser and following the operating-system preference by default.
  • Responsive design for desktop, tablet and mobile (collapsing columns, wrapping navigation, horizontally scrollable tables).
  • Branded favicon shown on every browser tab.

8. Security Considerations

  • Public key only: the browser uses Supabase's publishable key, which is safe to expose. The secret key and database password are never placed in the application.
  • Password hashing: passwords are hashed (SHA-256 with a salt) on the client before storage.
  • SQL injection: all database access goes through the Supabase client using parameterised methods (.eq, .insert, .update, .delete). No SQL is built from user input, so SQL injection is not possible through the application.
  • Input validation: usernames are restricted to a safe character whitelist.
  • Output escaping: user-supplied text is HTML-escaped before display, mitigating cross-site scripting (XSS).
  • Idle logout: sessions end automatically after 15 minutes of inactivity.
  • Current limitation: the login is a "simple gate" — Row Level Security policies are permissive, so a technically skilled user with the public key could reach the data directly. For stronger protection the system can be upgraded to Supabase Auth with restrictive policies.

9. Deployment

  1. Database: create a Supabase project and run the schema script (supabase/schema.sql) in the SQL Editor to create tables, security policies and Realtime.
  2. Configuration: set the Supabase project URL and publishable key in js/config.js.
  3. Hosting: push the repository to GitHub and enable GitHub Pages (Deploy from branch → main → root). The site publishes at https://<username>.github.io/<repo>/.
  4. Updates: every push to the main branch redeploys automatically.

10. Limitations & Future Enhancements

  • Meeting reminders only fire while an app tab is open (static hosting cannot push when closed). A future enhancement could add server-side or push-service reminders.
  • Upgrade from the simple login gate to full Supabase Authentication with restrictive Row Level Security.
  • Optional enhancements: weekly calendar view, recurring bookings, capacity-aware room suggestions, configurable working hours, and a pre-logout warning prompt.
